后端为一种语言生成代码。随 tsurara 提供的后端位于它的仓库中；其他语言的后端可以放在自己的仓库中，作为由 tsurara 启动的程序运行。本指南从一个空仓库开始，最终得到一个能通过 `tsurara test-backend` 的后端，以及一个能通过一致性测试向量的运行时。你只需要 `tsurara` 二进制文件。

## 1. 程序 {#1-the-program}

tsurara 会运行后端的命令两次，分别追加 `describe` 或 `generate`。两者都在 stdout 上打印一个 JSON 对象；`generate` 从 stdin 读取一个 JSON 对象。用户这样选择它：

```yaml
input: openapi.yaml
output: out
language:
  command: [node, path/to/backend.mjs]
  options: { package: petstore }   # 原样作为 `options` 传入
```

该命令在配置文件所在的目录中运行。

`describe` 打印程序所支持的内容：

```json
{
  "protocol": 2,
  "semVersions": [1],
  "markers": {
    "generated": "// Generated by my-backend. Do not edit.",
    "version": { "file": "Api.kt", "prefix": "// Requires my-runtime " },
    "sidecars": [".uid"]
  }
}
```

- `protocol`：1 或 2（2 允许 `generate` 返回清单）。`semVersions`：程序能理解的模型版本；当 tsurara 的模型版本不在其中时，tsurara 会报错停止，并给出两个版本。
- `markers.generated` 是后端写入的每个文件的第一行。tsurara 会删除以它开头的过时文件，`tsurara check` 会报告对这些文件的修改。`version`（可选）是记录代码所需运行时版本的行，`tsurara check` 会把它与已安装的运行时进行比较。`sidecars`（可选）是与过时文件一起删除的扩展名。

`generate` 读取 `{ "protocol", "semVersion", "model", "common", "options" }`，并打印 `{ "files": [{ "path", "contents" }], "warnings": [], "manifest": ... }`。路径相对于输出目录。`model` 是分析后的定义；其 JSON Schema 为 `spec/sem-model.schema.json`，请求的 JSON Schema 为 `spec/plugin-protocol.schema.json`（`tsurara spec <dir>` 会同时写出两者）。使用协议 2 时，`manifest`（可选）列出为每个 schema 和操作生成的名称，供 `extend` 钩子和插件使用（参见[插件](../plugins/#the-manifest)）。

## 2. 能力与名称 {#2-capabilities-and-names}

模型与 OpenAPI 很接近：联合类型、`allOf`、内联对象、可空性。大多数语言无法表达全部这些内容，而且来自定义的名称会互相冲突、撞上关键字，还需要转换大小写。tsurara 为自己的后端解决了这两个问题，当 `describe` 提出请求时，也会把同样的结果提供给你的后端：

```json
{
  "lowering": {
    "capabilities": {
      "inlineRecords": false, "structuralUnions": false, "taggedUnions": true,
      "intersections": false, "inheritance": "none", "literalTypes": false,
      "enums": "any", "tuples": false, "strictDecoding": false,
      "nullablePrimitives": true, "recursionByValue": false
    }
  },
  "naming": {
    "contexts": {
      "type": { "case": "pascal", "reserved": ["Any", "String"], "reservedSuffix": "Model" },
      "member": { "case": "camel", "reserved": ["class", "fun", "val"], "reservedSuffix": "_" },
      "constant": { "case": "screamingSnake" },
      "function": { "case": "camel" },
      "file": { "case": "pascal", "ascii": true }
    },
    "initialisms": ["ID", "URL"]
  }
}
```

这样 `generate` 还会收到：

- `lowered`：转换为你的语言可以写出的声明的模型：记录（仅当 `inheritance` 允许时才带有 `base`）、枚举、作为声明的带标签和不带标签的联合类型，以及别名。当能力声明不支持时，内联对象、交叉类型和结构化联合类型会消失，变成具名声明。类型表达式通过索引引用声明（`{ "named": { "decl": 3, "site": "received" } }`）。
- `names`：对 `lowered` 中的每个声明，按索引给出其类型 `name`、`file`（不含扩展名）和 `members`（按顺序排列的记录字段或枚举值）；对模型中的每个操作给出其 `function`。名称在需要的范围内唯一：类型名在整个输出中唯一，文件名在忽略大小写时也唯一，成员在其声明内唯一。

`naming` 中每个上下文可设置：`case`（`pascal`、`camel`、`snake`、`screamingSnake`、`kebab`、`preserve`）、`digitPrefix`（加在会以数字开头的名称前面；默认 `_`）、`upperPrefix`（加在不以大写字母开头的名称前面，Go 需要它；默认无）、`fallback`（用于不含字母的名称；默认 `value`）、`ascii`（其他字符变为 `u` 加其码点）、`reserved` 和 `reservedSuffix`（默认 `_`）。没有规则的上下文使用 `type` 的规则。需要超出这些的规则时，需要用 Rust 编写后端，它可以使用与 tsurara 相同的 crate（`tsurara-lower`、`tsurara-naming`；参见 `examples/backend-rust`）。

请从 `examples/backend-typescript/backend.mjs` 开始，这是一个单文件的完整后端。

## 3. 测试 {#3-testing}

```sh
tsurara test-backend --backend 'node backend.mjs' --check 'node check.mjs'
```

该命令会用你的后端生成 tsurara 边界情况语料库中的每个定义（冲突的名称、保留字、循环、判别字段、继承、multipart、Swagger 2.0 等），并在每个输出目录中运行 `--check`，同时设置 `TSURARA_OUTPUT` 和 `TSURARA_DEFINITION`。请用你的语言的编译器或 linter 作为检查（`go vet ./...`、`kotlinc`、`dotnet build`）。失败的定义会给出名称，其目录（定义、配置和输出）会被保留以便复现。`--definitions <dir>` 可添加你自己的定义或真实世界的定义；`--options` 以 JSON 形式传入 `options`；`--keep <dir>` 保留所有输出。

请在 CI 中用你所支持的 `tsurara` 版本运行它。

## 4. 运行时 {#4-the-runtime}

当序列化由运行时库负责时，生成的代码可以保持精简：生成的函数传入操作的描述（OperationDef），运行时构建请求、发送请求，并把响应读成结果。tsurara 的所有运行时都实现了同一份契约，你的运行时也应如此：

```sh
tsurara spec ./spec
```

该命令写出这个 tsurara 版本的契约：`README.md`（OperationDef、结果种类、序列化、TypeDef、Mock 传输层）、JSON Schema，以及 `conformance/`，即你的运行时测试要运行的向量（请求、响应、序列、TypeDef、Mock 路由；格式见 `conformance/README.md`）。请把运行时分为类型层（声明所需的内容：可选和可空标记、联合类型辅助函数）和客户端层，这样生成的类型无需 HTTP 客户端也能使用。

## 5. 版本 {#5-versions}

- `semVersion`（模型）、`manifestVersion` 和协议只在发生不兼容变更时才会改变；兼容的新增（新的可选字段）不会改变它们，因此请忽略你不认识的字段。`spec/CHANGELOG.md` 记录了每一次变更。
- 在 `semVersions` 中列出你支持的所有模型版本。当 tsurara 切换到新版本时，它会报错停止并给出两个版本，用户就知道需要升级你的后端。

## 仓库结构示例 {#a-repository-layout}

```
my-backend/
  backend/          程序（任意语言）
  runtime/          运行时库，带有运行 spec/conformance 的测试
  spec/             来自 `tsurara spec`，与其来源的 tsurara 版本一起提交
  .github/workflows/ci.yml
```

```yaml
# .github/workflows/ci.yml
jobs:
  test:
    steps:
      - uses: actions/checkout@v5
      - run: npm install --global tsurara@0.1.2   # 你所支持版本的 `tsurara` 二进制文件
      - run: tsurara test-backend --backend 'node backend/backend.mjs' --check 'node backend/check.mjs'
      - run: npm test --prefix runtime
```
