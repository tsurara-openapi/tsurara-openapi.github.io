A backend generates code for one language. Backends that ship with tsurara live in its repository; a backend for another language can live in its own repository and run as a program that tsurara starts. This guide goes from an empty repository to a backend that passes `tsurara test-backend` and a runtime that passes the conformance vectors. You need only the `tsurara` binary.

## 1. The program

tsurara runs the backend's command twice, appending `describe` or `generate`. Both print one JSON object on stdout; `generate` reads one on stdin. Users select it with:

```yaml
input: openapi.yaml
output: out
language:
  command: [node, path/to/backend.mjs]
  options: { package: petstore }   # passed through as `options`
```

The command runs in the directory of the configuration file.

`describe` prints what the program speaks:

```json
{
  "protocol": 2,
  "semVersions": [1],
  "markers": {
    "generated": "// Generated by my-backend. Do not edit.",
    "version": { "file": "Api.kt", "prefix": "// Requires my-runtime " },
    "sidecars": [".uid"]
  }
}
```

- `protocol`: 1 or 2 (2 lets `generate` return a manifest). `semVersions`: the model versions the program understands; tsurara stops with an error naming both versions when its model is not listed.
- `markers.generated` is the first line of every file the backend writes. tsurara deletes stale files that start with it, and `tsurara check` reports edits to them. `version` (optional) is the line that records the runtime version the code needs, which `tsurara check` compares with the installed runtime. `sidecars` (optional) are extensions deleted together with a stale file.

`generate` reads `{ "protocol", "semVersion", "model", "common", "options" }` and prints `{ "files": [{ "path", "contents" }], "warnings": [], "manifest": ... }`. Paths are relative to the output directory. `model` is the analyzed definition; its JSON Schema is `spec/sem-model.schema.json` and the request's is `spec/plugin-protocol.schema.json` (`tsurara spec <dir>` writes both). With protocol 2, `manifest` (optional) lists the names generated for each schema and operation, for `extend` hooks and plugins (see [Plugins](../plugins/#the-manifest)).

## 2. Capabilities and names

The model is close to OpenAPI: unions, `allOf`, inline objects, nullability. Most languages cannot express all of it, and names from a definition collide, hit keywords and need casing. tsurara solves both for its own backends, and gives the same to yours when `describe` asks for it:

```json
{
  "lowering": {
    "capabilities": {
      "inlineRecords": false, "structuralUnions": false, "taggedUnions": true,
      "intersections": false, "inheritance": "none", "literalTypes": false,
      "enums": "any", "tuples": false, "strictDecoding": false,
      "nullablePrimitives": true, "recursionByValue": false
    }
  },
  "naming": {
    "contexts": {
      "type": { "case": "pascal", "reserved": ["Any", "String"], "reservedSuffix": "Model" },
      "member": { "case": "camel", "reserved": ["class", "fun", "val"], "reservedSuffix": "_" },
      "constant": { "case": "screamingSnake" },
      "function": { "case": "camel" },
      "file": { "case": "pascal", "ascii": true }
    },
    "initialisms": ["ID", "URL"]
  }
}
```

`generate` then also receives:

- `lowered`: the model as declarations your language can write: records (with a `base` only when `inheritance` allows it), enums, tagged and untagged unions as declarations, and aliases. Inline objects, intersections and structural unions are gone when the capabilities say so: they become named declarations. Type expressions name declarations by index (`{ "named": { "decl": 3, "site": "received" } }`).
- `names`: for each declaration of `lowered`, by index, its type `name`, its `file` (without extension) and its `members` (record fields or enum values, in order), and for each operation of the model its `function`. Names are unique where they must be: type names across the output, file names also ignoring case, members within their declaration.

Per context of `naming`: `case` (`pascal`, `camel`, `snake`, `screamingSnake`, `kebab`, `preserve`), `digitPrefix` (before a name that would start with a digit; default `_`), `upperPrefix` (before a name that does not start with an upper-case letter, as Go needs; default none), `fallback` (for a name with no letters; default `value`), `ascii` (other characters become `u` and their code point), `reserved` and `reservedSuffix` (default `_`). A context without rules uses those of `type`. Rules beyond these need a backend in Rust, which uses the same crates as tsurara (`tsurara-lower`, `tsurara-naming`; see `examples/backend-rust`).

Start from `examples/backend-typescript/backend.mjs`, a complete backend in one file.

## 3. Testing

```sh
tsurara test-backend --backend 'node backend.mjs' --check 'node check.mjs'
```

generates every definition of tsurara's edge-case corpus (names that collide, reserved words, cycles, discriminators, inheritance, multipart, Swagger 2.0, ...) with your backend, and runs `--check` in each output directory, with `TSURARA_OUTPUT` and `TSURARA_DEFINITION` set. Use your language's compiler or linter as the check (`go vet ./...`, `kotlinc`, `dotnet build`). A failing definition is named, and its directory (definition, configuration and output) is kept for reproduction. `--definitions <dir>` adds your own definitions, or real-world ones; `--options` passes `options` as JSON; `--keep <dir>` keeps every output.

Run it in CI with the `tsurara` version you support.

## 4. The runtime

Generated code stays small when serialization lives in a runtime library: generated functions pass a description of the operation (an OperationDef) and the runtime builds the request, sends it and reads the response into a result. tsurara's runtimes all implement the same contract, and yours should too:

```sh
tsurara spec ./spec
```

writes the contract of this tsurara version: `README.md` (OperationDefs, the result kinds, serialization, TypeDefs, mock transports), the JSON Schemas, and `conformance/`, the vectors your runtime's tests run (requests, responses, sequences, TypeDefs, mock routing; `conformance/README.md` describes the format). Split the runtime into a types layer (what declarations need: optional and nullable markers, union helpers) and a client layer, so that generated types work without the HTTP client.

## 5. Versions

- `semVersion` (the model), `manifestVersion` and the protocol change only incompatibly; compatible additions (new optional fields) keep them, so ignore fields you do not know. `spec/CHANGELOG.md` records every change.
- List every model version you support in `semVersions`. When tsurara moves to a new one, it stops with an error naming both versions, so users know to upgrade your backend.

## A repository layout

```
my-backend/
  backend/          The program (any language)
  runtime/          The runtime library, with tests that run spec/conformance
  spec/             From `tsurara spec`, committed with the tsurara version it came from
  .github/workflows/ci.yml
```

```yaml
# .github/workflows/ci.yml
jobs:
  test:
    steps:
      - uses: actions/checkout@v5
      - run: npm install --global tsurara@0.1.0   # the `tsurara` binary of the version you support
      - run: tsurara test-backend --backend 'node backend/backend.mjs' --check 'node backend/check.mjs'
      - run: npm test --prefix runtime
```
