バックエンドは1つの言語のコードを生成します。tsuraraに同梱されているバックエンドはtsuraraのリポジトリにあります。ほかの言語のバックエンドは独自のリポジトリに置き、tsuraraが起動するプログラムとして動かせます。このガイドでは、空のリポジトリから始めて、`tsurara test-backend` を通るバックエンドと、適合性テストのベクターを通るランタイムを作ります。必要なのは `tsurara` のバイナリだけです。

## 1. プログラム {#1-the-program}

tsuraraは、バックエンドのコマンドに `describe` または `generate` を付け足して2回実行します。どちらも標準出力に1つのJSONオブジェクトを出力し、`generate` は標準入力から1つのJSONオブジェクトを読みます。利用者は次のように選びます。

```yaml
input: openapi.yaml
output: out
language:
  command: [node, path/to/backend.mjs]
  options: { package: petstore }   # `options` としてそのまま渡される
```

コマンドは設定ファイルのあるディレクトリで実行されます。

`describe` は、プログラムが話す内容を出力します。

```json
{
  "protocol": 2,
  "semVersions": [1],
  "markers": {
    "generated": "// Generated by my-backend. Do not edit.",
    "version": { "file": "Api.kt", "prefix": "// Requires my-runtime " },
    "sidecars": [".uid"]
  }
}
```

- `protocol`：1か2（2では `generate` がマニフェストを返せます）。`semVersions`：プログラムが理解できるモデルのバージョン。tsuraraのモデルのバージョンが挙がっていなければ、tsuraraは両方のバージョンを示すエラーで止まります。
- `markers.generated` は、バックエンドが書くすべてのファイルの最初の行です。tsuraraはこの行で始まる古いファイルを削除し、`tsurara check` はそれらへの編集を報告します。`version`（省略可能）は、コードが必要とするランタイムのバージョンを記録する行で、`tsurara check` がインストール済みのランタイムと比べます。`sidecars`（省略可能）は、古いファイルと一緒に削除する拡張子です。

`generate` は `{ "protocol", "semVersion", "model", "common", "options" }` を読み、`{ "files": [{ "path", "contents" }], "warnings": [], "manifest": ... }` を出力します。パスは出力先ディレクトリからの相対パスです。`model` は解析済みの定義で、そのJSON Schemaは `spec/sem-model.schema.json`、リクエストのJSON Schemaは `spec/plugin-protocol.schema.json` です（`tsurara spec <dir>` が両方を書き出します）。プロトコル2では、`manifest`（省略可能）にスキーマと操作ごとに生成した名前を並べます。これは `extend` フックとプラグインが使います（[プラグイン](../plugins/#the-manifest)を参照）。

## 2. 能力と名前 {#2-capabilities-and-names}

モデルはOpenAPIに近く、union、`allOf`、インラインのオブジェクト、nullを含みます。たいていの言語はそのすべてを表現できません。また、定義から来る名前は衝突し、キーワードとぶつかり、大文字小文字の変換も必要です。tsuraraは自分のバックエンドのためにこの両方を解決していて、`describe` で求めれば、あなたのバックエンドにも同じものを渡します。

```json
{
  "lowering": {
    "capabilities": {
      "inlineRecords": false, "structuralUnions": false, "taggedUnions": true,
      "intersections": false, "inheritance": "none", "literalTypes": false,
      "enums": "any", "tuples": false, "strictDecoding": false,
      "nullablePrimitives": true, "recursionByValue": false
    }
  },
  "naming": {
    "contexts": {
      "type": { "case": "pascal", "reserved": ["Any", "String"], "reservedSuffix": "Model" },
      "member": { "case": "camel", "reserved": ["class", "fun", "val"], "reservedSuffix": "_" },
      "constant": { "case": "screamingSnake" },
      "function": { "case": "camel" },
      "file": { "case": "pascal", "ascii": true }
    },
    "initialisms": ["ID", "URL"]
  }
}
```

すると `generate` は次のものも受け取ります。

- `lowered`：その言語で書ける宣言にしたモデル。レコード（`inheritance` が許すときだけ `base` を持ちます）、enum、宣言としてのタグ付きunionとタグなしunion、エイリアスです。能力の指定に応じて、インラインのオブジェクト、交差型、構造的なunionはなくなり、名前付きの宣言になります。型の式は、宣言をインデックスで参照します（`{ "named": { "decl": 3, "site": "received" } }`）。
- `names`：`lowered` の各宣言について、インデックスごとに型の `name`、`file`（拡張子なし）、`members`（レコードのフィールドかenumの値を順に）を、モデルの各操作について `function` を持ちます。名前は必要な範囲で一意です。型の名前は出力全体で、ファイル名は大文字小文字を無視しても、メンバーは宣言の中で一意です。

`naming` のコンテキストごとに指定できるもの：`case`（`pascal`、`camel`、`snake`、`screamingSnake`、`kebab`、`preserve`）、`digitPrefix`（数字で始まってしまう名前の前に付けるもの。デフォルトは `_`）、`upperPrefix`（大文字で始まらない名前の前に付けるもの。Goで必要です。デフォルトはなし）、`fallback`（文字を含まない名前の代わり。デフォルトは `value`）、`ascii`（ほかの文字を `u` とそのコードポイントに置き換える）、`reserved` と `reservedSuffix`（デフォルトは `_`）。規則のないコンテキストは `type` の規則を使います。これ以外の規則が必要なら、Rustでバックエンドを書きます。tsuraraと同じクレート（`tsurara-lower`、`tsurara-naming`）を使えます（`examples/backend-rust` を参照）。

1ファイルで完結したバックエンド `examples/backend-typescript/backend.mjs` から始めてください。

## 3. テスト {#3-testing}

```sh
tsurara test-backend --backend 'node backend.mjs' --check 'node check.mjs'
```

このコマンドは、tsuraraのエッジケースのコーパス（衝突する名前、予約語、循環、判別子、継承、マルチパート、Swagger 2.0など）のすべての定義をあなたのバックエンドで生成し、各出力ディレクトリで `--check` を実行します。そのとき `TSURARA_OUTPUT` と `TSURARA_DEFINITION` が設定されます。検査には、その言語のコンパイラーやリンター（`go vet ./...`、`kotlinc`、`dotnet build`）を使ってください。失敗した定義は名前で示され、再現用にそのディレクトリ（定義、設定、出力）が残ります。`--definitions <dir>` で独自の定義や実在の定義を追加でき、`--options` で `options` をJSONで渡せ、`--keep <dir>` ですべての出力を残せます。

CIでは、対応するバージョンの `tsurara` で実行してください。

## 4. ランタイム {#4-the-runtime}

シリアライズをランタイムライブラリに任せれば、生成コードは小さく保てます。生成された関数は操作の記述（OperationDef）を渡し、ランタイムがリクエストを組み立てて送信し、レスポンスを読んで結果にします。tsuraraのランタイムはどれも同じ契約を実装しています。あなたのランタイムもそうしてください。

```sh
tsurara spec ./spec
```

このコマンドは、このバージョンのtsuraraの契約を書き出します。`README.md`（OperationDef、結果の種類、シリアライズ、TypeDef、モックのトランスポート）、JSON Schema、そしてランタイムのテストで実行するベクターの入った `conformance/`（リクエスト、レスポンス、シーケンス、TypeDef、モックのルーティング。形式は `conformance/README.md` にあります）です。ランタイムは、型の層（宣言が必要とするもの：省略可能やnullを表す型、unionのヘルパー）とクライアントの層に分けてください。そうすれば、生成された型がHTTPクライアントなしで使えます。

## 5. バージョン {#5-versions}

- `semVersion`（モデル）、`manifestVersion`、プロトコルが変わるのは互換性のない変更のときだけです。互換性のある追加（省略可能な新しいフィールド）では変わらないので、知らないフィールドは無視してください。すべての変更は `spec/CHANGELOG.md` に記録されます。
- 対応するモデルのバージョンをすべて `semVersions` に挙げてください。tsuraraが新しいバージョンに移ると、両方のバージョンを示すエラーで止まるので、利用者はバックエンドを更新すべきだとわかります。

## リポジトリの構成例 {#a-repository-layout}

```
my-backend/
  backend/          プログラム（言語は問わない）
  runtime/          ランタイムライブラリ。spec/conformance を実行するテスト付き
  spec/             `tsurara spec` の出力。生成元の tsurara のバージョンとともにコミットする
  .github/workflows/ci.yml
```

```yaml
# .github/workflows/ci.yml
jobs:
  test:
    steps:
      - uses: actions/checkout@v5
      - run: npm install --global tsurara@0.1.0   # 対応するバージョンの `tsurara` バイナリ
      - run: tsurara test-backend --backend 'node backend/backend.mjs' --check 'node backend/check.mjs'
      - run: npm test --prefix runtime
```
